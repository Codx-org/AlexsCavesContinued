## The silent-override trap (the spine of this report)

A mod method written **without `@Override`** keeps compiling after vanilla changes the
supertype's parameter list, silently stops being called from that version up, and **nothing**
reports it — not javac, not `verify_mixins.py`, not a green boot, not a green build. Six of the
twelve reported items were instances of it.

`scripts/override_audit.py` is the detector, with **two limits that both bit during this cycle**:

1. **It reads COMPILED classes.** Its output is stale for any node not freshly recompiled — a
   fix can be verifiably in source and still be reported on 19 nodes. Recompile, then audit.
2. **It under-reports.** `MetalBarrelBlock.use` and `RemoteDetonatorItem`'s methods were absent
   from its 1673 findings. Treat the output as a lower bound and read reported classes directly.

Known false-positive families still to suppress inside it. The 58/58 run is now at **916
findings, every one of them in a family below** — zero unexplained rows. (It was 917 while
`DesolateDaggerItem.getMaxDamage` was still outstanding; that row is the one that has since been
fixed and is gone, which is what the drop of exactly one is.)

| family | count | why it is not a defect |
|---|---|---|
| `lerpMotion(DDD)` | 336 | a real bridge IS emitted by `stonecutter.gradle.kts` ~3095 |
| `*Model.animate(IAnimatedEntity)` | 242 | Citadel's own method; pure name collision with `Model.animate(AnimationState, …)` |
| `getToolModifiedState` | 84 | **loader-package mismatch** — see below |
| `trigger(ServerPlayer)` | 58 | `ACAdvancementTrigger`'s mod-internal convenience overload |
| `scale(...)` | 58 | erasure bridge (`BrainiacRenderer` et al.) |
| `getEquipmentSlot()` | 42 | `GalenaGauntletItem`; dead upstream too |
| `getAttributeModifiers` | 28 | the seven already-gated items |
| `canBeRiddenUnderFluidType` | 26 | **loader-package mismatch** |
| `canPerformAction` | 13 | **loader-package mismatch** |
| `getExpDrop` | 11 | `RadrockUraniumOreBlock`, already two-armed |
| `getQuads` | 10 | **loader-package mismatch** (`fabric/forge/**` `BakedModelWrapper`) |
| `getDefaultAttributeModifiers` | 7 | the same seven items |
| `getSoundType` | 1 | `PewenBranchBlock`; both arms verified live (see below) |
| ~~`getMaxDamage`~~ | 0 | `DesolateDaggerItem` — **this one was real** and is now FIXED; the row no longer appears |

**The loader-package mismatch is the audit's third limit.** It resolves the mod's declared
descriptor against whichever supertype it can find, which for these hooks is the **Forge**
(`net.minecraftforge.*`) one — while the class it is reading was compiled for NeoForge
(`net.neoforged.neoforge.common.ItemAbility`, `…neoforge.fluids.FluidType`) or for Fabric (the
mod's own `fabric/forge/**` stand-ins). Same method, different package, so the descriptors never
match and never will. Not a defect; do not chase these again.

### ⚠️ `scripts/mcjavap.py` had a blind spot, and it caused two wrong band boundaries

`jar_for(mc)` only matched loom's **`<loader>-<mc>-<build>-minecraft-merged/`** directory. A
plain **Fabric** node's jar lives under the *shared* `minecraft-merged/` directory with the MC
version in the **child** folder name (`minecraft-merged/1.21.2-loom.mappings…/…jar`), so the
four MC versions this matrix reaches on Fabric only — `1.20.3`, `1.20.5`, `1.21.2` (and
`1.21.2-neoforge`, which has no Forge sibling either) — resolved to nothing. Every caller that
treats a miss as "skip" silently stopped covering them, so their bands were inferred from
neighbours and both landed **one MC version too high**:

| what | recorded | truth (javap'd out of the real jar) |
|---|---|---|
| `Block.getCloneItemStack` takes `LevelReader` | ≥1.20.4 | **≥1.20.3** (1.20.1/1.20.2 take `BlockGetter`) |
| `LivingEntity.getBaseExperienceReward` takes `ServerLevel` | ≥1.21.3 | **≥1.21.2** (1.21.1 is `protected int getBaseExperienceReward()`) |

Both were hard compile failures on exactly those nodes, which is the only reason they were
caught. `jar_for` now falls back to the shared layout.

⚠️ **`scripts/override_audit.py` carried its OWN copy of the same buggy lookup** (a second
`vanilla_jar()` at ~line 159), so fixing `mcjavap.py` alone changed nothing — the audit still
printed *"skipped … 1.20.3-fabric 1.20.5-fabric 1.21.2-fabric 1.21.2-neoforge"*. It now
`import mcjavap` and delegates, translating `jar_for`'s `SystemExit` back to `None`, so there is
**one** place that knows loom's two cache layouts. First run with real 58/58 coverage:
**917 findings, no skip line** (was 860 over 54 nodes). The four newly-visible nodes contributed
57 rows, of which all but two are the known families; the two singletons were each worth a look
and split one-and-one:

- `PewenBranchBlock.getSoundType(BlockState, LevelReader, BlockPos, Entity)` on `1.21.2-neoforge`
  — **not a defect.** Probed every NeoForge build in the matrix (20.4 → 26.2) plus Forge 1.20.1:
  `IBlockExtension`/`IForgeBlock` declares that exact four-argument overload on **all 36**
  Forge/NeoForge nodes, and the `//? if fabric` arm supplies vanilla's one-argument form.
- `DesolateDaggerItem.getMaxDamage(ItemStack)` on `1.20.3-fabric` — **real**, and worse than the
  single node suggests. See the worklist.

**The rest of the tree was then swept for the same error** (any band stated as starting at
1.20.4, 1.20.6 or 1.21.3 — i.e. one above a Fabric-only version — shares the blind spot). There
are exactly **two** such `//?` gates in `src/main/java` (`NuclearFurnaceResultSlot:52`,

## Report #6 — smithing table crash: SOLVED

ℹ️ **The report's trailing *"Anvil and enchantment table is not"* is consistent with the cause and
needs no separate investigation.** The crash is an *entity preview* built by hand — only
`SmithingScreen` does that. The anvil and the enchantment table render no entity, so they were
never going to crash, which is exactly what the reporter observed.

**Reproduced locally on `26.2-fabric`** (dev client, `/setblock ~ ~1 ~2 minecraft:smithing_table`
then right-click) — the report needs no log from the reporter any more.

```
Description: Rendering entity in world
java.lang.NullPointerException: Cannot invoke "…LivingEntity.getUUID()" because "rendered" is null
    at …client.event.ClientEvents.acPreRenderLiving(ClientEvents.java:159)
    at …client.event.ClientEvents.preRenderLiving(ClientEvents.java:198)
    at …fabric.event.ACEventBus.post(ACEventBus.java:105)
    at LivingEntityRenderer.handler$…$ac_fabricPreRenderLiving(LivingEntityRenderer.java:2564)
    at ArmorStandRenderer.submit(ArmorStandRenderer.java:73)
    at EntityRenderDispatcher.submit(EntityRenderDispatcher.java:154)
    at GuiEntityRenderer.renderToTexture(GuiEntityRenderer.java:39)
    at PictureInPictureRenderer.prepare / GuiRenderer.preparePictureInPictureState / GuiRenderer.render
```

**Cause — a render state that never came from an entity.** From 1.21.2 the loaders' render events
hand out an `EntityRenderState` instead of the entity, so this tree recovers the entity from the
duck that `mixin.renderstate.EntityRendererMixin` stamps at `EntityRenderer#extractRenderState`
HEAD (`ACStateAccess`). That covers every state vanilla *extracts*. It does not cover a state
vanilla **constructs by hand** — and 1.21.9 moved the GUI's entity previews onto picture-in-picture
rendering, where (javap'd on 26.2) `SmithingScreen`'s constructor does exactly that:

- `SmithingScreen.<init>`: `new ArmorStandRenderState()`, then `entityType` / `showBasePlate` /
  `showArms` / `xRot` / `bodyRot` assigned field-by-field; `updateArmorStandPreview(ItemStack)`
  fills the equipment slots. **`extractRenderState` never runs, and there is no armour-stand entity
  anywhere** — the preview is pure data.
- `SmithingScreen.extractRenderState` passes that state to `GuiGraphicsExtractor.entity(...)`;
  `GuiEntityRenderer.renderToTexture` then calls `EntityRenderDispatcher.submit(state, …)` →
  `ArmorStandRenderer.submit` → the mod's `RenderLivingEvent.Pre` dispatcher, with a null entity.

That is why the **anvil and the enchanting table are fine** — they render no entity — while the
smithing table dies on open. Same reason the player inventory is fine: `InventoryScreen` builds its
preview through `EntityRenderer#createRenderState(entity, partialTick)`, which *does* call
`extractRenderState`, so the duck is stamped there.

**Fix.** `ClientEvents.acPreRenderLiving` returns `false` and `acPostRenderLiving` returns early
when the entity is null — there is nothing either hook can do for a preview. Both were the only
**unguarded** `ACStateAccess.entity(...)` dereferences in the tree; audited all 11 consumers:

| consumer | status |
|---|---|
| `ClientEvents.acPreRenderLiving` / `acPostRenderLiving` | **were unguarded — fixed** |
| `StateRenderLayer.draw` | already `if (entity == null) return;` |
| `ACArmorRenderProperties`, `HumanoidArmorLayerMixin` ×3, `citadel/LivingEntityRendererMixin`, `citadel/HumanoidModelMixin` ×4 | `instanceof`-guarded ⇒ null-safe |
| `ArrowRenderer.getTextureLocation` | unguarded, but no GUI path constructs an arrow state |
| `LivingEntityRendererEventsMixin` ×6 | reads `partialTick`, not the entity |

**Band: 1.21.9 → 26.2, all three loaders** (the versions with GUI picture-in-picture entity
rendering). Compile-verified on `26.2-{fabric,forge,neoforge}`, `1.21.8-fabric` and `1.20.1-forge`.

**Runtime-verified on the patched build** (2026-08-23, `26.2-fabric`, same reproduction —
`/setblock ~3 ~1 ~ minecraft:smithing_table`, `/tp @s ~ ~ ~ -90 3`, then use): the screen opens to
"Upgrade Gear" and **the armour-stand preview draws** — i.e. the entity-less render state still
reaches `ArmorStandRenderer.submit`, the guard simply declines to do anything with it, which is the
intended behaviour rather than the preview being suppressed. Client process alive afterwards, no new
file in `versions/26.2-fabric/run/crash-reports/`.

## Report #5 — the raycat glow: NOT a regression

**Verdict: the raycat renders the same on every render era this tree spans.** Matched-rig A/B on
`1.20.1-forge` (= upstream, the reference), `1.21.5-fabric` (first *RenderPipeline* node) and
`26.2-fabric` (deferred-submit + reversed-Z): identical halo extent, identical textured body with a
bright emissive face, no hard-edged rectangle around the glow, and the same brightness. Whatever the
reporter photographed, it is not a cross-version drift in the irradiated effect — **their MC version
and a viewable screenshot are now the blocker**.

⚠️ **The single-frame brightness metric that started this was measuring the shader, not the port.**

## Report #2 — the primordial "pinwheel": it is the Ambersol shine, drawn correctly

Reproduced in-world on `26.2-fabric` at `[810, 28, 1167]` (`/locate biome alexscaves:primordial_caves`):
white starburst wedges radiating from a single vertex, embedded in the cave walls. At 500 % it reads as
geometry collapsing to a point — the classic look of a degenerate or NaN vertex — which is why it was
filed as undiagnosed. It is neither.

**It is `AmbersolBlockRenderer`.** The renderer fans `lights` (a `pos.asLong()`-seeded `4..8`) triangles
around the block centre, billboarded to the camera, each drawn as a degenerate quad
`origin, left, right, left` into `ACRenderTypes.getAmbersolShine()`. The origin vertex is
`(255,254,233, α230)` and both outer corners are `(215,89,32, α0)`, blended
`SRC_ALPHA, ONE, ONE, ONE_MINUS_SRC_ALPHA` — additive. Barycentric interpolation gives constant alpha
*across* a wedge and falloff only *along* it, so **the hard straight edges are inherent to the shape**,
not a symptom.

### What was checked, and how

Sealed A/B with `scripts/block_shots.sh` — one block against open sky, pinned time, spectator, exact
position *and* rotation, five-block volume cleared, four consecutive frames:

| check | `1.20.1-forge` (upstream parity) | `26.2-fabric` | verdict |
|---|---|---|---|
| wedge count / fan geometry | 9 wedges | 9 wedges | identical |
| added light, recovered by diffing an `air` background frame | warm, `R>G>B` | warm, `R>G>B` (`(106,81,13)` near the block, decaying to nothing) | identical |
| occluded by solid stone (`scripts/block_occlusion_test.sh`) | plain stone, no bleed | plain stone, no bleed | identical |

The 26.2 frame *looks* whiter only because that rig player carries permanent night vision: an additive
draw over a brightened background saturates. Diffing the background out removes the difference entirely.

### Why it reads as a bug to a player

The fan is billboarded at the **block's** depth plane and spreads several blocks sideways, so wedges
emerge into open air with their source block hidden behind rock — a starburst with no visible cause.
That is upstream art direction, and it has a client toggle already
(`AlexsCaves.CLIENT_CONFIG.ambersolShines`, checked at the `AFTER_TRANSLUCENT_BLOCKS` dispatch in
`ClientEvents`). ⚠️ **Do not "fix" it** — any change here diverges from upstream for every node.

What the reporter almost certainly saw on shipped `1.0.0` is the row above it: **the reversed-Z depth
bug**, which made every render type in the mod x-ray through terrain on 26.2 and is already fixed

## Report #9/#9b — the compendium and the spelunkery table: four silent bugs, stacked

Reproduced on `26.2-fabric`: `/give @s alexscaves:cave_book`, press use — the world darkens,
the HUD dims, **nothing is drawn**, and the screen eats input until Escape. That a screen really
was open (rather than it merely being night) was proved by sending `/say SCREEN-OPEN-TEST`, which
never appeared because the chat key was swallowed; after Escape, `/say AFTER-ESCAPE` appeared
and the world was bright daylight.

Nothing is logged for either bug. The whole search had to be done by instrumentation.

**Bug 1 — the book model never left its recorder.** From 1.21.6 a screen cannot draw a 3D model
inline; it submits a `PictureInPictureRenderState` and a `PictureInPictureRenderer` rasterises it
into its own texture. Three temporary `ACBOOKDBG` probes (state constructor, mixin lookup,
`renderToTexture`) all fired every frame — `state submitted 427x240`, `lookup hit, original=null`,
`renderToTexture running` — so the whole picture-in-picture chain worked and the failure was
downstream of it. It was in `CaveBookPipRenderer.renderToTexture`'s `>=26.2` arm, which built an
`ACSubmitBuffers` around the frame's `SubmitNodeCollector` and **never called `flush()`**. An
`ACSubmitBuffers` *records*; nothing reaches the frame until the recording is handed to the
collector. 26.2-only, because the band below is handed a real immediate-mode `BufferSource` that
the game ends itself. Every one of the other 18 construction sites in the tree flushes;
`scripts/submit_flush_audit.py` now keeps that invariant (19 sites, 0 misses).

**Bug 2 — the pages were drawn into the wrong buffer source.** With bug 1 fixed the book drew,
with **blank pages**. `PageRenderer.renderPage` ignored the buffer source the book model was
being drawn into and fetched its own, `Minecraft.getInstance().renderBuffers().bufferSource()`.
Below 26.2 those are the same object, so it never mattered. On 26.2 there is no
`Minecraft#renderBuffers()` and that call resolves to `ACRenderContext.bufferSource()` — the
**level** pass's shared source, whose collector is pushed only inside `LevelRenderer#submitFeatures`
and is therefore `null` while the book is being rasterised. `ACClientCompat.drawInBatch`'s 26.2 arm
returns early on a null collector, so every glyph, page number, item and widget was dropped without
a word. Fixed by threading the real buffer source down
`renderBookModel` → `renderBookContents` → `renderForPageType` → `PageRenderer#renderPage` →
`BookWidget#render`, widening those signatures from `MultiBufferSource.BufferSource` to
`MultiBufferSource`. A no-op on every band below 26.2, where the threaded object is the one that
was being fetched anyway.

⚠️ **The general shape, worth carrying to any other GUI that draws a model.** On 26.2 "draw" means
"record, then hand the recording to *this* pass's collector". A draw call that reaches the wrong
collector, or none, is not an error — it is a no-op. So the two questions to ask of any legacy
render body on that version are *who flushes this?* and *whose collector am I on?*, and neither
has an answer in the log.

**Bug 3 — vanilla deleted `Font#adjustColor` at 1.21.6, so every `0xRRGGBB` text colour became
alpha 0.** With bugs 1 and 2 fixed the book drew, page furniture and all, and the pages were
**still blank**. A temporary `ACBOOKDBG_HIDE_MODEL` flag in `CaveBookScreen` removed the book
model entirely and the text still did not appear, which ruled out occlusion and proved the glyphs
were never rendered rather than being drawn behind something.

The cause is in vanilla, not in the mod. Up to and including **1.21.5**, both `Font#drawInternal`
overloads *and* `drawInBatch8xOutline` (on the colour **and** the outline colour, never on
`backgroundColor`) opened with

```java
private static int adjustColor(int c) { return (c & 0xFC000000) == 0 ? ARGB.opaque(c) : c; }
```

From **1.21.6** that method does not exist and the colour goes straight to the glyph quads, so a
literal with no alpha byte means alpha 0: the text is submitted, batched and drawn completely
transparent. **Nothing is logged and nothing throws.** Verified by `javap` on the loader-patched
jar of all 22 MC versions in the matrix — fixup present `1.20.1`…`1.21.5`, absent
`1.21.6`…`26.2`. `GuiGraphics` has no fixup of its own on 26.2 either.

That is a **22-node** bug, not a 26.2 one, and it is why the *spelunkery table* (report #9) looked
dead too: its title, its "attempts" line, its highlight and its word buttons are all
`0X99876C`/`0X000000`/`4210752` literals. On 26.2 the two failures were indistinguishable, because
bug 2 was already dropping the same glyphs.

The fix is one helper, `ACColors.opaque`, doing exactly what vanilla used to:

```java
public static int opaque(int argb) { return (argb & 0xFC000000) == 0 ? argb | 0xFF000000 : argb; }
```

Below 1.21.6 it is a no-op the game would have performed anyway, **so call sites need no `//?`
gate** — one ungated wrap is right on all 58 nodes. Applied inside `ACClientCompat`'s three text
wrappers (so every site that already goes through them is fixed at once) and at the handful of raw
`GuiGraphics.drawString` sites that do not: `SpelunkeryTableScreen` (×6), `SpelunkeryTableWordButton`,
`NuclearFurnaceScreen` (×2), plus `CaveMapRenderer`'s two `0X87695B`/`0XEBDCC2` constants.
`scripts/text_alpha_audit.py` is the standing detector — it parses the colour argument of every
text-draw call site, skips the ones that route through the wrapper, and fails on any literal whose
alpha byte is empty. Currently 0.

**Bug 4 — the 26.2 `String` text path lost `§` formatting.** With bug 3 fixed the pages finally
drew, with every legacy formatting code printed as two literal glyphs. `ACClientCompat`'s `>=26.2`
`drawInBatch(Font, String, …)` arm was building its sequence with
`FormattedCharSequence.forward(text, Style.EMPTY)`, which is `StringDecomposer.iterate` — a
**verbatim** walk. Vanilla's own `String` path is `bidirectionalShaping` followed by
`StringDecomposer.iterateFormatted`, i.e. `§` codes are *style*, not characters. Swapped to that.
Only the 26.2 arm was ever wrong; the band below hands the string to `Font#drawInBatch` itself.

⚠️ **The reusable lesson is bug 3, and it is not specific to this mod.** Any mod carrying
`0xRRGGBB` text colours from before 1.21.6 draws invisible text from 1.21.6 up, silently. The tell
is text that is *missing* rather than *wrong*, on a version boundary that has nothing to do with
the GUI code that stopped working. `ClientSackOfSatingTooltip` already carried a local comment
noting the trap on one line without generalising it — one call site had been noticed and fixed
years before the other forty.

### Root cause: `@Redirect` and `@ModifyConstant` are EXCLUSIVE injectors

Only one mod may redirect a given instruction. Mixin keeps whichever applicator ran **first**,
logs `"@Redirect conflict. Skipping …"` for the loser, and the loser's `"defaultRequire": 1`
then throws `InjectionError: Critical injection failure: … (0/1) succeeded`. That fails the whole
class transformation, so **both** mods die — the crash is not "AMC's fault" or "Citadel's fault",
it is whichever of the two lost the race.

⚠️ **`@ModifyConstant` collides the same way** — it is implemented as a `RedirectInjector`
subclass. This is why the Citadel repro crashed at a *server* mixin (`ServerLevel#tickTime`'s
`1L`) long before any render mixin ran, and why the fix had to widen from 2 files to 6.

Because Citadel is **vendored** here (93 relocated classes + 13 mixins, see `docs/notes/citadel.md`),
this mod duplicates Citadel's entire mixin set against vanilla. So it is not one unlucky
instruction: *every* exclusive injector in the overlap collides with real Citadel, and AMC — which
depends on real Citadel and carries its own copy of the outline hook — collides on the render one.

### The fix: MixinExtras composing injectors

`@WrapOperation` and `@ModifyExpressionValue` are **late** injectors, applied after every vanilla
redirect. They wrap whatever the instruction has already become, so the other mod's redirect runs
as `original.call(...)` and both hooks survive. Both accept `method` / `at` / `slice` / `remap` /
`require` / `expect` / `allow` / `order` (confirmed by javap on `mixinextras-fabric-0.5.3.jar`), so
the conversion is annotation-name + one extra handler parameter, with the Stonecutter-gated
`method` arms and `expect` counts untouched. `@ModifyExpressionValue` reaches a constant via
`@At(value = "CONSTANT", args = "longValue=1")` — the `args` spelling, not `constant = @Constant`.

MixinExtras is available on every node: Fabric Loader and NeoForge bundle it, and
`build.forgeg.gradle.kts` already ships `mixinextras-forge` on Forge builds below 60.1.11.

Six vendored-Citadel mixins converted:

| file | was | now |
|---|---|---|
| `mixin/client/citadel/OutlineColorMixin.java` | `@Redirect` `Entity;getTeamColor()I` | `@WrapOperation` |
| `mixin/client/citadel/SkyTimeOfDayMixin.java` | `@Redirect` `ClientLevel;getTimeOfDay(F)F` | `@WrapOperation` |
| `mixin/citadel/ServerLevelMixin.java` | `@ModifyConstant` `longValue = 1L` | `@ModifyExpressionValue` `args = "longValue=1"` |
| `mixin/client/citadel/ClientLevelMixin.java` | `@ModifyConstant` `longValue = 1L` | same |
| `mixin/citadel/MinecraftServerMixin.java` | `@ModifyConstant` `longValue = 50L`, `expect = 4` | `@ModifyExpressionValue` `args = "longValue=50"`, `expect = 4` |
| `mixin/client/citadel/SplashRendererMixin.java` | `@ModifyConstant` `intValue = -256` / `16776960` | `@ModifyExpressionValue` `args = "intValue=-256"` / `"intValue=16776960"` |

`SkyTimeOfDayMixin`'s handler deliberately does **not** call `original` — it replaces the time of
day outright, which is what the `@Redirect` did.

`mixin/client/citadel/LevelRendererMixin.java` was deliberately **left** as a `@Redirect`
(`OutlineBufferSource;endOutlineBatch()V`). Citadel's counterpart there is an `@Inject`, so there
is no conflict, and the ≥1.21.2 arms select through a regex (`/lambda\$addMainPass\$/`) plus
loader-specific `method_62214` spellings that a conversion would put at risk for no reported gain.

is not one. Proof it is the rig: javap on the loom-patched named jar finds **0** occurrences of
`f_135042_`, while `citadel.refmap.json` maps `addAdditionalSaveData`→`m_7380_` etc. The valid
route is loom's own remapper, via a throwaway `"modLocalRuntime"(files(<jar>))` dependency driven
by a `-P` property. `build.forgeg.gradle.kts` already documents the identical trap for codxlib.
The probe used here was **reverted** after the run; do not look for it in the tree.

### W4 — the acid crash, and why no `//?` gate could have fixed it

Player's report, NeoForge **26.1.2.97**, `alexscaves@1.0.0`:

```
java.lang.IllegalArgumentException: Cannot look up tracker by tag for non-vanilla fluid:
    TagKey[minecraft:fluid / alexscaves:acid]
  at EntityFluidInteraction.getFluidTypeByTag(EntityFluidInteraction.java:255)
  at Entity.isEyeInFluid(Entity.java:1636)
  at ACFluids.isEyeInAcid(ACFluids.java:103)
  at ClientEvents.fogColor(ClientEvents.java:1153)
```

**NeoForge reintroduced `FluidType` into `EntityFluidInteraction` between builds `26.1.2.87` and
`26.1.2.97` — same MC version, both live in the wild.** On `.97` the `trackerByFluid` map is keyed
by `FluidType`, the constructor's `Set<TagKey<Fluid>>` loop is commented out, and every
`TagKey`-shaped method routes through `getFluidTypeByTag`, which hard-throws for anything that is
not water or lava. The mod's `EntityMixin#ac_trackModFluids` `@ModifyArg` widening of the tracked
tag set therefore stopped taking effect, and `Entity#isEyeInFluid(TagKey)` became a guaranteed
throw for `alexscaves:acid`.

⚠️ **This tracks the loader BUILD, not the MC version.** Stonecutter gates and
`replacements.string` rules are both keyed on the MC version, so *neither can express it* — one
jar has to be correct on `.87` and `.97` at once.

The fix is to stop asking the loader. `ACFluids` is now **ungated** (all seven `//? if >=26 ||
fabric` arms deleted) and self-computes from `Level#getFluidState` — pure vanilla API, byte-identical
across all 58 nodes:

- `fluidHeight(entity, tag)` walks the entity's deflated bounding box, skipping unloaded chunks, and
  returns the deepest matching fluid surface above `box.minY`. A `null` tag means *any* fluid.
- `isEyeInFluid(entity, tag)` samples the single block at eye level (minus vanilla's `0.11111111`
  drop) and compares the fluid's surface height against the eye.

Three side benefits: one implementation instead of two, the **active node now exercises it** (it
used to compile only the loader-delegating arm), and `isInAnyFluid`/`maxFluidHeight` regained
third-party-fluid awareness that the `>=26` rewrite had narrowed to a fixed list.

`EntityMixin` is deliberately **unchanged**. Its `>=26` `@ModifyArg` is now redundant for queries but
harmless (the `<init>(Ljava/util/Set;)V` target is unchanged even on `.97`), and its `fabric && <26`
`@Inject` at TAIL of `updateInWaterStateAndDoFluidPushing` is what actually supplies **push
physics** on Fabric's 18 sub-26 nodes — that one must stay.

### The bytecode proof that the crash path is gone (26.1.2-neoforge, compiled against .97)

`javap -p -c` over **every** compiled mod class on that node, grepping for the whole family
(`isEyeInFluid`, `getFluidHeight`, `EntityFluidInteraction`, `getFluidTypeByTag`,
`getFluidTypeHeight`, `isInFluidType`, `getMaxHeightFluidType`, `getEyeInFluidType`):

- `ACFluids` itself calls **only** `Level.getFluidState`, `Level.hasChunkAt`,
  `FluidState.{getHeight,isEmpty,is}`, `AABB.deflate`, `BlockPos.{containing,getY}`,
  `BlockPos$MutableBlockPos.set` and `Entity.{level,getBoundingBox,getEyeY,getX,getZ}`. Nothing
  from the loader, nothing that can throw.
- Exactly **two** vanilla `isEyeInFluid(TagKey)` call sites survive anywhere in the mod —
  `CommonEvents:370` (diving helmet) and `MagneticWeaponEntity:340` — and **both pass
  `FluidTags.WATER`**, which is one of the two tags `.97`'s `getFluidTypeByTag` still answers.
- Every other hit in the tree is a comment or javadoc.

- `EntityMixin`'s `>=26` `ac_trackModFluids` `@ModifyArg` is **inert on `.97`, not dangerous**.
  `javap`'d straight out of `minecraft-patched-26.1.2.97.jar`: the
  `EntityFluidInteraction(Set<TagKey<Fluid>>)` constructor still takes the set and still iterates it,
  but the loop body is empty (`checkcast TagKey; astore_3; goto` — the element is loaded and
  dropped), so widening the set adds nothing and, crucially, never reaches `getFluidTypeByTag`. The
  mixin's `@At` target descriptor is unchanged, which is why `verify_mixins.py` is green on that node.
- The accepted-tag set of `.97`'s `getFluidTypeByTag` is exactly **`FluidTags.WATER` and
  `FluidTags.LAVA`**, compared by reference (`if_acmpne`), everything else falling straight to
  `new IllegalArgumentException`. Four `TagKey`-shaped methods route through it —
  `applyCurrentTo`, `getFluidHeight(TagKey)`, `isInFluid(TagKey)`, `isEyeInFluid(TagKey)` — so any
  one of the four with a mod tag is the same crash.

So on `.97` there is no reachable path to `Cannot look up tracker by tag for non-vanilla fluid`.
This is worth re-running after any change to `ACFluids` or `EntityMixin`: the standing rule here is
that a green build proves the shapes exist, not that nothing calls the broken one.

### One deliberate divergence from vanilla in the rewrite

Vanilla's `Entity#updateFluidOnEyes` carries a **boat exemption**: if the vehicle is a `Boat`, is
not itself underwater, and its bounding box straddles the eye Y, the fluid-at-eyes check is skipped
entirely. `ACFluids#isEyeInFluid` does **not** reproduce it, on purpose.

Reproducing it properly needs an `instanceof Boat` — and the class is `Boat` below 1.21.2 and
`AbstractBoat` from there, so it would be another gate. The tempting version-neutral approximation
("skip when *any* vehicle's bbox contains the eye") is **worse than omitting it**: this mod has
large rideable mobs whose bounding boxes swallow the rider's eye, so that rule would suppress acid
fog for anyone riding one, which is a real bug. Vanilla's exemption, by contrast, almost never
fires — a floating boat keeps the eye above the surface, and a submerged one fails
`isUnderWater()`. The whole cost of leaving it out is at most a frame of fog while a boat bobs in
acid. Do not "fix" this without the gated `Boat`/`AbstractBoat` check.

### ⚠️ Fabric API was missing as a dependency on EVERY fabric version — 1.0.0 included

Caught by the user after the 1.0.1 upload. `scripts/modrinth_upload.py` hardcoded a
single-element dependency list holding only `CODXLIB_PROJECT_ID`, while every fabric jar's
generated `fabric.mod.json` declares a hard per-MC-version floor (`fabric-api >=0.92.11+1.20.1`
on 1.20.1 … `>=0.155.2+26.2` on 26.2). Modrinth metadata and the jar manifest therefore
disagreed: launchers had no reason to install Fabric API, so the mod installed and then failed
to start.

- Fixed in the uploader by a `version_dependencies(loader)` helper — Fabric API (`P7dR8mSH`)
  is appended on **fabric nodes only**, project-level, so Forge/NeoForge keep codxlib alone.
- `scripts/fix_fabric_api_dep.py` retro-patches published versions and is idempotent (it
  re-reads each with `GET /v2/version/{id}`, never the cached listing). Ran it over the live
  project: **44/44 fabric versions fixed — 22 on 1.0.1 and 22 on the already-shipped 1.0.0.**
- ⚠️ **The PATCH read-back lags.** The first pass reported 12 "not readable back"; all 12 were
  fine on a re-run, and a third pass read `already-ok=44 fixed=0 failed=0`. **Re-run the
  idempotent fixer rather than investigating a failure.**
- ⚠️ **CurseForge cannot be fixed this way.** CF relations have no API field and carry no
  version, so `codxlib` *and* `fabric-api` both have to be added by hand in the web UI.

## Post-1.0.2 report: "some creatures are able to attack themselves … they fly away"

**Audited and not reproduced in this tree; guarded anyway.** Full sweep of every route by which a
mob here could be handed itself:

### #1 — the Cave Compendium's shading: `EMISSIVE` is not "unlit"

The book model drew with a hard bright/dark step per face (~0.48 between adjacent faces, measured
off the screenshot) because it was going through a type that still applied vanilla's cardinal
(diffuse) lighting. **`EMISSIVE` gates only the lightmap; only the `NO_CARDINAL_LIGHTING` define
removes `minecraft_mix_light(...)`** — confirmed in `core/entity.vsh` on 1.21.5, 1.21.6, 1.21.8,
1.21.9, 1.21.10, 1.21.11, 26.1, 26.1.2 and 26.2.

Blast radius **23 of 58 nodes**, from two unrelated causes that happen to overlap:

- All **22 Fabric** nodes — the stand-in under `fabric/forge/client/` returned vanilla's
  entity-translucent-*emissive* type, which is the wrong switch.
- **`26.2-forge`** — Forge 65.1.0 rewrote its own unlit factories onto plain
  `RenderPipelines.ENTITY_TRANSLUCENT`. ⚠️ **NeoForge did not**: 26.2.0.66 still names
  `neoforge:pipeline/entity_unlit_translucent`, still declares `NO_CARDINAL_LIGHTING` and still
  binds the lightmap (javap'd). An earlier revision of that stand-in's javadoc claimed the
  opposite for both loaders and was wrong; do not trust it if it resurfaces in a diff.

Fixed by owning the type: `ACInternalShaders.ENTITY_UNLIT_TRANSLUCENT` (entity-translucent plus
the one define, lightmap kept — i.e. NeoForge's shape) and a three-armed

three particles.

### #6 — the cave map drew black: `TextureManager.register` stopped loading at 1.21.4

### #9 — the quarry demolished its own frame: `encapsulatingFullBlocks` is a different box

`AABB.encapsulatingFullBlocks`. Those are **not the same box**: the old constructor took the two
positions as plain coordinates, the new one takes min/max and then **adds 1 to each maximum** so

six-double constructor, which exists unchanged across the whole matrix and sorts its own corners,
so **no gate at all**. The other eleven call sites are render bounds and entity searches, where the
extra block was invisible but no more correct.

geometry going to `ACRenderTypes.IRRADIATED_OUTPUT`, i.e. into that effect's own `RenderTarget`.

### #8 — the glow flash: a fresh `RenderType` per call, and 25 more like it

The flash is **not** the designed pulse (`LayerGlow` computes `sin(ageInTicks * 0.2F) * 0.15F + 0.5F`,
a gentle ±0.15 swing), and it is not the `spikeDownAmount > 0` second pass. What it is: on some frames
the additive glow is drawn **twice**.

Everything upstream of the GPU was eliminated first, on `26.2-fabric`, and the negative results are
worth not re-walking:

- **The layer's inputs are constant.** 1500 probe lines, 1500 distinct `age` values, one
  `LayerGlow.render` call per frame; `spikeDown=0.0` and `powered=true` on every frame.
- **It is not the `EQUAL` depth test.** Swapping `ACInternalShaders.EYES_ALPHA` from
  `depthEqual(…, true)` to `depth(…, false)` did not stop it. Per-pixel comparison of the two states:
  **0** pixels lit in the bright frame but dark in the dim one — no geometry appears or disappears —
  2336 pixels lit in both but brighter, **median ratio 2.06**. An exact doubling.
- **The mod submits once and vanilla replays once.** 4282 replays, replays-per-recorder histogram
  `[(1, 4282)]`; `ACSubmitBuffers.flush` strictly alternating `BGBGBG…`, 2000 body and 2000 glow
  submissions, one of each per frame.

The one thing that differed: the body's render type was **one instance across all 2000 frames**
(memoized) while `eye_alpha` produced **2000 distinct instance ids**. `ACRenderTypes.getEyesAlphaEnabled`
built a fresh `RenderType` on every call, on both arms.

That matters because **`RenderType` declares neither `equals` nor `hashCode` on any version in this
range** (checked with javap; nor does `RenderType$CompositeRenderType`). So every map vanilla keys by
one compares by **identity**:

- `MultiBufferSource$BufferSource#startedBuilders` and `#fixedBuffers` — a per-call instance misses
  the lookup every frame, the shared batch is torn down and rebuilt, and a batch ended under a key
  that is no longer the one in the map is left for a later flush.
- from 26.2 only, `RenderTypeFeatureRenderer$Group#getVertexBuilder`'s `lastRenderType == renderType`
  fast path — which is why the symptom is *worse* on 26.2. That class does not exist below 26.2;
  1.21.9–26.1 replay custom geometry through `CustomFeatureRenderer.render(SubmitNodeCollection,
  MultiBufferSource$BufferSource)` instead. **Do not assume the 26.2 mechanism is the whole story on
  the lower nodes — it is the `BufferSource` maps there.**

Measured both ways, with `/tick freeze` so every frame should be identical:

| Node | upstream (fresh per call) | memoized |
|---|---|---|
| `26.2-fabric` | 10 frames, **2 distinct states**, 819 px differing by up to 161 | **12/12 byte-identical** |
| `1.21.11-fabric` | **2 of 30** frames spike peak green 58 → **213** — repeated in a second 30-frame run, same 2/30 | **0 of 30**; frame-to-frame energy swing 1.151× → 1.007× |

The 1.21.11 run is an A/B/A inside **one** client boot, toggled by a file the factory checks, so
camera, tick and scene are identical across all 90 frames.

**The fix is not one method.** An audit of `ACRenderTypes` found **26** static factories building a
`RenderType` per call — every one of them upstream's. They now go through one `TYPE_CACHE`
(`ConcurrentHashMap`, keyed on the method name plus its arguments); each `getXxx` is a thin wrapper
over a private `buildXxx` holding the original, still-gated body, so no `//?` arm moved. Among the 26
are `getSubmarineLights`/`getSubmarineMask` (fourth-wave #2, submarine flicker), `getRaygunRay`
(fourth-wave #5, raygun freeze/lag) and `getRadiationGlow` — **re-test those three before assuming
they are still open.**

The general trap, worth carrying to any mod: **a factory that builds a `RenderType` per call is a
latent double-draw and a per-frame leak into an identity-keyed map, on every MC version.** It only
became *visible* here because the type's blend is additive. Vanilla ships every one of its own types
as a singleton or behind `Util.memoize`; matching that is the whole fix.

```
  com/github/alexmodguy/alexscaves/citadel/server/world/ModifiableTickRateServer.resetGlobalTickLengthMs
```

**Root cause: vendoring relocates classes, but not what a mixin merges into a vanilla one.** Both
Citadel's `MinecraftServerMixin` and our vendored copy `implements ModifiableTickRateServer`, and
both interfaces declare `default void resetGlobalTickLengthMs()`. `MinecraftServer` then inherits
two unrelated defaults with the same signature, which the JVM refuses to resolve — so the class
cannot load at all and the game dies before a single line of mod code runs. **It is not
version-banded**: every node of every loader has this, the reporter simply had the pair installed.

Verified against the real jar rather than from memory (`javap -p` over
`citadel-2.7.1-1.21.1.jar`), which also produced the full collision list:

| channel | what collided | how it fails |
|---|---|---|
| interface `default` | `resetGlobalTickLengthMs()` | ⛔ `IncompatibleClassChangeError` at class load |
| merged methods | `setGlobalTickLengthMs(J)V`, `getMasterMs()J`, `get`/`setCitadelEntityData`, and **every** `citadel_*` injector handler on both sides (`citadel_beforeServerTick`, `masterTick`, `citadel_registerData`, `citadel_write`/`readAdditional`, `citadel_guardEntityTick`, `citadel_clientSetDayTime`, `citadel_poseRight`/`LeftArm`, `citadel_setupRotations`, `citadel_render_*`, `citadel_resize`, `citadel_renderLevel_*`, `citadel_initOutline`, `citadel_pre`/`postRenderSplashText`, …) — byte-identical names, since ours are copies | Mixin keeps the higher-priority one and drops the other, silently; the loser's interface calls then read the winner's fields |

| shared string id | `CitadelServerData`'s `SavedData` identifier `"citadel_world_data"` | `ClassCastException` in `CitadelServerData.get` **every server tick** — see below |

### The second bug, which the first one was hiding

### The fix

Everything this mod merges into a vanilla class is now unique to it: interface methods `ac`-prefixed

rename pass.

### The report does NOT reproduce as "no glow"

- **memoized:** 290,794 – 408,198, peak 255

Indistinguishable. Do not re-open "the render-type cache made the glow dimmer" — it did not, on the

### What the reporter is actually seeing

Upstream never made a charged tremorzilla brighter. `LayerGlow` pulses
`sin(ageInTicks * 0.2) * 0.15 + 0.5` → alpha **0.35 … 0.65** whether or not `isPowered()`; being
powered only swaps in a glow texture with **6,191 more lit pixels** (bbox x 29–391, y 105–427 of the
512² sheet). The blend is additive, so alpha *is* brightness — and the plates therefore sat at ~half
brightness permanently.

Until `1.0.4` that went unnoticed **because the uncached `RenderType` had the pass drawn twice on
some frames**, which is precisely the flashing that `1.0.4` fixed (`1.21.11-fabric`, measured then:

lighting up*. Both halves of the report are the same event seen from two sides.

### The fix

One line in `TremorzillaRenderer.LayerGlow`: a powered tremorzilla pulses **0.70 … 1.00** instead of
0.35 … 0.65. Unpowered is left exactly as upstream had it, so only the "fully charged" state changes
— which is the state the report is about. 1.0 is the ceiling for a single additive pass, i.e. this
recovers the peak the double draw used to reach *without* a second pass, so it cannot flicker.

Measured on `1.21.8-fabric`, same scene, client restart only, two independent tremorzillas (both had
recharged to powered by then — the entity adds 1 charge/tick, so a `Charge:0` summon is powered again
inside 50 s, which is a useful two-sample control):

| | green energy, mob A | mob B |
|---|---|---|
| before | 154,048 – 256,800 | 208,068 – 337,868 |
| after | 301,428 – 397,992 | 414,425 – 528,855 |

≈ **1.6–2.0×**, the top of the range compressed by the green channel clipping at 255.

### The reusable lesson

**Removing an accidental double draw is a visible brightness regression, not a neutral fix.** Any
additive pass that was being drawn twice was, in effect, shipping at 2× alpha, and that is the
brightness players calibrated on. When a "drawn twice" bug is fixed, check whether the *intended*
single-pass value still looks like the effect it is meant to be — and if not, raise it deliberately,
where it is one readable number, instead of leaving it to an identity-keyed vanilla map.

## Eighth wave (2026-08-26) — a startup crash in a 743-mod pack, `mclo.gs/t1PKU1o`

> Hi i'm still getting a crash using alex's caves, alex's mobs as well as both matching compat mods
> for farmers delight. both alexs mobs & caves work alone with their matching delight mod, just not
> all together still. I've made sure to update to the latest files & still get the same thing
> unfortunately. i've tried with & without citadel as well just in case lol

MC **26.2 / Fabric**, ACC **1.0.5** (so *not* the sixth wave's Citadel fix), Prism, **743 mods**.

### It is not the mods the reporter named

The reporter's bisection is confounded in a way worth writing down, because the next reporter will
do the same thing: **the crash happens inside Alex's Caves' own block registration**, so removing
Alex's Caves removes it trivially, and every other combination they tried still contained the mod
that actually adds the offending blockstate property. Reproduced here on `26.2-fabric` with a dev
build plus `alexsmobs 2.1.7` + `accdelight` + `amcdelight` + `farmersdelight`: **`Done (1.657s)`,
48 mods, clean.** Adding `ferritecore 9.0.0`: **`Done (1.707s)`, 49 mods, clean.** None of the four
named mods is involved.

### The stack, and what it actually says

```
Caused by: java.lang.NullPointerException: Cannot invoke
    "net.minecraft.world.phys.shapes.VoxelShape.isEmpty()" because "this.collisionShape" is null
  at net.minecraft.world.level.block.state.BlockBehaviour$BlockStateBase$Cache.<init>(BlockBehaviour.java:1324)
  at net.minecraft.world.level.block.state.BlockBehaviour$BlockStateBase.initCache(BlockBehaviour.java:882)
  at net.minecraft.world.level.block.Blocks.…$fabric-registry-sync-v0$lambda$initShapeCache$0$0(Blocks.java:1242)
  at net.minecraft.core.MappedRegistry.register(MappedRegistry.java:131)
  …
  at com.github.alexmodguy.alexscaves.fabric.registries.DeferredRegister$Entry.resolve(DeferredRegister.java:284)
  at com.github.alexmodguy.alexscaves.AlexsCaves.<init>(AlexsCaves.java:256)
```

Three things are packed into that:

1. **`Cache.<init>` dereferences the shape it just asked the block for.** On 26.2 it assigns
   `this.collisionShape = block.getCollisionShape(state, EmptyBlockGetter.INSTANCE, BlockPos.ZERO,
   CollisionContext.empty())` and calls `.isEmpty()` on the next line. **A block whose
   `getCollisionShape` can return `null` is a hard NPE**, with no message naming the block.
2. **Fabric API's `fabric-registry-sync-v0` runs that eagerly.** Its `initShapeCache` mixin puts a
   `RegistryEntryAddedCallback` on `BuiltInRegistries.BLOCK` from `Blocks.<clinit>`, which walks
   **every possible state** of each newly registered block *at registration time*. So this fires
   inside our own `DeferredRegister` flush, in the mod constructor, long before a world exists —
   which is why it is a startup crash rather than a place-a-block crash, and why it is Fabric-only
   in practice even though the defect is loader-neutral.
3. **The frame the crash does not name is the one that matters**: something in the pack had added a
   ninth blockstate property to `AbyssmarineWallBlock`.

### The defect: a shape cache keyed on whole-`BlockState` identity

`AbyssmarineWallBlock` (upstream code, unchanged since 1.20.1) held two
`Map<BlockState, VoxelShape>`s built by enumerating its own eight properties off
`this.defaultBlockState()` — 2 (`UP`) × 3⁴ (four `WallSide`s) × 15 (`DISTANCE`) × 2 (`ACTIVE`) × 2
(`WATERLOGGED`) = **9720** keys per map — and both getters were a bare `map.get(state)`.

`BlockState` equality is identity. The instant *any other mod* adds a property to this block, the
state definition's cartesian product grows, none of the new states is a key in that map, `get`
returns `null`, and vanilla NPEs on it. Nothing about the enumeration is wrong; the *key* is.

### Proof, not inference

Mechanically audited all **80** shape-getter overrides under `src/main/java`. Exactly two can return
`null`, and both are in this class. (`SulfurBudBlock` keys on `FACING` and puts all six directions;
`ThinBoneBlock` / `DinosaurChopBlock` / `BoneRibsBlock` / `RebarBlock` hold maps but compute-then-return.)

Then reproduced it directly: **pre-fix code plus one extra `BooleanProperty` on the block**, standing
in for the unidentified third-party mod, on `:26.2-fabric:runServer` — the crash comes back
**frame-for-frame identical** to the reporter's, down to `Cache.<init>(BlockBehaviour.java:1324)` →
`initCache(:882)` → `initShapeCache$0$0(Blocks.java:1242)` → … → `AlexsCaves.<init>(:256)`. Only the
per-build mixin hash suffixes differ.

### The fix

Both maps become 162-entry `VoxelShape[]`s indexed by the five properties that actually change the
outline (`UP` + the four `WallSide`s); the four altar/water properties never did. Every getter goes
through `shapeIndex(BlockState)`, which *reads named properties* instead of hashing the whole state,
so a foreign property is now simply irrelevant. `createBlockStateDefinition`, `tick`, `updateShape`,
`getStateForPlacement` and `applyWallShape` are byte-unchanged; no `//?` gate moved. Side benefit:
19,440 map entries per abyssmarine wall block collapse to 324 array slots.

**Verified**: with the fix in place *and* the simulated foreign property still added — plus
`lithium 0.25.3` and `moreculling 1.8.1` in `run/mods/`, the two other plausible shape-manglers —
`:26.2-fabric:runServer` reaches **`Done (1.518s)`**, 49 mods, clean.

The specific mod among the 743 that injects the property was never identified, and does not need to
be: 31 candidate `26.2-fabric` jars were pulled and scanned for `createBlockStateDefinition` /
`WallBlock` references and every hit was a mod defining its *own* blocks (`diagonal_corners`,
`walllanterns`, `swinginglanterns`, `slablight` and `ferritecore` were each read and ruled out).
The AC-side defect is proven, and after the fix it does not matter which mod it was.

### The reusable lesson

**A shape cache keyed on whole-`BlockState` identity is a latent hard crash the moment any other mod
adds a property to that block.** Key the cache on the properties that actually affect the shape —
never on the state object — and remember that on Fabric the crash lands during *your* registration
call, in a stack that names Fabric API and vanilla and never names the block.

### #1 — the id window, and why sharing a `Properties` closed it

From 1.21.2 a `BlockBehaviour.Properties` carries the block's id, and anything reading
`effectiveDrops()` / `effectiveDescriptionId()` before it is set throws `NullPointerException: Block
id not set`. This tree already stamps the id from `ACRegistryIds.constructing` (a `ThreadLocal` set
around each `DeferredRegister` supplier) via `BlockPropertiesMixin` / `ItemPropertiesMixin`.

Two things defeated it here:

1. **The stamp ran too late.** It was applied on the *builder calls*, so a `Properties` handed
   straight to a constructor without another builder call kept a null id.
2. **`ACBlockRegistry` held 22 shared `public static final … _PROPERTIES` constants**, built in
   `<clinit>` — i.e. outside every block's constructing window — and used by ~162 registrations.
   Whichever block used one first got the id; the rest inherited it or nothing.

Fix: both mixins gained an `@Inject(method = "<init>", at = @At("RETURN"))` that stamps the pending
id at construction, and all 22 constants became **per-use factory methods**
(`GINGERBREAD_PROPERTIES()`), with all ~162 references rewritten to calls. Nothing else in the class
moved.

**Why only Farmer's Delight Refabricated surfaced it**: Forgified Fabric API's
`FabricBlock$FabricProperties.blockIdOrThrow` is called from FD's own block construction, which runs
*earlier* than any vanilla/NeoForge path that reads the id. Everything else asked late enough that
the existing stamp had already run.

**Reproduced and re-verified**: `:26.1.2-neoforge:runServer` with Connector 3.0.0-beta.6, FFAPI
0.155.2, Launchpad 1.9.2 and FD Refabricated 3.6.17 in `run/mods/` reaches `Done (0.236s)` with zero
`Block id not set`.

### #3 / #10 / #12 — asking the world for a fluid during world generation

`EntityMixin`'s `ac_isInWater` / `ac_isEyeInFluid` (added in `1.0.3` so mod fluids count for
eye-in-fluid and fluid height) called `ACFluids.modFluidHeight` / `isEyeInModFluid`, which called
`Level#getFluidState` → `Level#getChunkAt` → `ServerChunkCache#getChunk`.

`Entity#isInWater` is reached during worldgen by `StructureTemplate.placeEntities` → `Entity.save`.
Off the main thread `ServerChunkCache.getChunk` posts to its `MainThreadExecutor` and `join()`s, so:

- **the stall** (#3, #10): every worldgen worker that saves a structure entity blocks until some
  other chunk finishes generating. Single-player exploration hides it; Chunky + C2ME turns it into
  worker-on-worker contention — the reporter's spark profile put **~19%** of worker time there, with
  throughput dropping from thousands of chunks/s to single digits.
- **the crash** (#12): the posted work is a *chunk generation*, run on the chunk-source main-thread
  executor, for a chunk whose neighbours are not loaded — `WorldGenRegion.getChunk` then throws
  `IllegalStateException: Requested chunk unavailable during world generation`, wrapped as
  `Exception generating new chunk`. That is exactly the reporter's stack: `class_3898.method_60445`
  under `class_3215$class_4212` (`ServerChunkCache$MainThreadExecutor`).

Fix: both helpers now resolve the chunk with `level.getChunkSource().getChunkNow(cx, cz)` — never
loads, never blocks, returns null for an absent chunk — cache it per column in the scan loop, and
`continue` on null. A class-javadoc paragraph records that this is a **correctness** fix, not an
optimisation, so nobody "simplifies" it back to `getFluidState`.

**Reproduced, and the trigger is a vanilla structure, not an AC one.** A same-seed A/B on
`1.21.11-fabric` (`level-seed=20250819`, a fresh world each run, then sixteen
`forceload add` commands covering chunks −32..31 × −32..31):

| | post-fix | pre-fix |
|---|---|---|
| chunks generated | **4624** | 60-odd, then nothing |
| `world/region` bytes | 41,658,550, quiescent | 2,278,754, frozen for 60 s |
| RCON | answered throughout | stopped answering |
| worldgen errors in log | 0 | server wedged before one could be thrown |

`jstack` on the wedged pre-fix server names the whole path, and there is no AC code in it above our
own frame:

```
OceanRuinPieces$OceanRuinPiece.handleDataMarker  →  ServerLevelAccessor.addFreshEntityWithPassengers
  →  WorldGenRegion.addFreshEntity  →  ProtoChunk.addEntity  →  Entity.save
  →  Zombie.addAdditionalSaveData  →  Entity.isInWater  →  ac_isInWater
  →  ACFluids.modFluidHeight  →  Level.getFluidState  →  ServerChunkCache.getChunk
  →  CompletableFuture.join()          [thread: Worker-Main-14]
```

…while the **server thread** sat in `ServerChunkCache$MainThreadExecutor.managedBlock` running the

`ModCompatBridge.afterAllModsLoaded` reflects into
`SurfaceRuleManager.addToDefaultSurfaceRulesAtStage(RuleCategory, RuleStage, int, SurfaceRules$RuleSource)`
and `addSurfaceRules(RuleCategory, String, SurfaceRules$RuleSource)`. TerraBlender `26.2.0.0.2`
replaced the `RuleSource` parameter with `SurfaceRuleManager$RuleBuilder`, which
`extends Function<HolderGetter<Biome>, SurfaceRules$RuleSource>`, so the old lookup threw
`NoSuchMethodException` and AC fell back to the built-in merge TerraBlender can override.

Fix: try the legacy signature first, and on `NoSuchMethodException` resolve
`terrablender.api.SurfaceRuleManager$RuleBuilder` and build the argument with a
`java.lang.reflect.Proxy` — `apply` returns the rule, `equals`/`hashCode`/`toString` are handled
explicitly, and anything else goes to `InvocationHandler.invokeDefault`. No compile-time dependency
on TerraBlender is added, which is the point of the whole bridge.

### #8 — a present-but-empty `accessTransformers` key makes Forge load NO access transformer

`mclo.gs/NwQOJOR`, Forge 1.20.1, only `alexscaves-1.0.5-forge+1.20.1` and `codxlib-1.5.1` installed:
`IllegalAccessError` on `SimpleCookingSerializer$CookieBaker` from `ACRecipeRegistry.java:39`.

`LoaderMetadata.kt`'s `ForgeManifest` declared `accessTransformers` and `ForgeLike.generateManifest`
set it to `emptyList()`, so the generated `mods.toml` shipped a literal `accessTransformers = [ ]`.
Forge's `ModFile` falls back to `META-INF/accesstransformer.cfg` **only when the key is absent** —
present-and-empty means "this mod has zero access transformers", so the file loom had already put
there was never read, and every AT-widened member stayed inaccessible.

was wrong in the way that matters: *deliberately absent* is the requirement. Fixed by deleting the
field from `ForgeManifest`, deleting the now-unused `ForgeAccessTransformer` data class, and
dropping the assignment, with a comment stating why. NeoForge was unaffected (it resolves the file
regardless), which is why this only ever showed up on Forge.

### #1 — a biome source that learned its level only while generating

`MultiNoiseBiomeSourceMixin` places AC's cave biomes by asking `ACBiomeRarity` whether the sampled
quart falls in one of its Voronoi cells. That question needs the **world seed** and the
**dimension**, and `getNoiseBiome(x, y, z, sampler)` is handed neither — so the source has to
remember which level it belongs to.

It learned that from `ChunkStatusMixin` alone, i.e. only while terrain was actively being generated.
Two holes follow directly:

- **A world with no generation happening this session** — a re-joined singleplayer world, a
  pre-generated server, or simply a player standing still — leaves the seed at `0` and the dimension
  at `null`.
- **More than one dimension loaded** leaves whichever level generated most recently, so an overworld
  query can be answered against the nether's key.

The cave map asks `ACBiomeRarity` the rarity question directly, over a wide radius, and gets the
layout for the *right* seed. The biome source, answering from a stale or zero seed, had placed the
biome somewhere else entirely — so the two disagreed and the map reported "not nearby". `/locate
biome` goes through the biome source's own index and is therefore self-consistent, which is exactly
why it kept working and is the detail that identifies the defect.

Fix: the source resolves its own level **once**, the first time it is asked, by walking
`ServerLifecycleHooks.getCurrentServer().getAllLevels()` for the level whose chunk generator holds
*this* biome source (`getChunkSource().getGenerator().getBiomeSource() == (Object) this`). That is
authoritative and cannot go stale. `ac_resolvedOwningLevel` then freezes both fields — the two
setters become no-ops — so `ChunkStatusMixin` survives only as the fast path for before the server is
reachable, and for any biome source no level owns. A failed walk does not set the flag, so a level
list caught mid-change simply retries on the next sample.

### #2 — the Nuclear Furnace demolished itself while being built

Placing the furnace runs an assembly pass that converts the 3×3×3 of component blocks into the
multiblock. Each conversion used a full `setBlockAndUpdate` / default-flag update, which makes
vanilla re-run `canSurvive` on every neighbour — including the component blocks that had not been
converted yet. A component whose neighbours are half-converted does not survive, so it popped, which
invalidated the next one, and the structure unwound as fast as it was built.

Fix: `NuclearFurnaceComponentBlock` now assembles with
`UPDATE_NEIGHBORS | UPDATE_CLIENTS | UPDATE_KNOWN_SHAPE`. `UPDATE_KNOWN_SHAPE` is the flag that
suppresses exactly the shape/`canSurvive` cascade while leaving the client sync and the neighbour
notification intact, so the finished multiblock still behaves identically once assembly completes.

### #4b — dinosaurs shaking their heads

`DinosaurEntity` set `yHeadRot` from the look controller every tick but never moved `yBodyRot` toward

idle, the head clamped against the body limit, snapped back, and clamped again — the reported violent
shake.

Fix: a `followHeadWithBody()` reproducing vanilla's damping (turn the body by the clamped overshoot,
capped at `getHeadRotSpeed()`, then re-clamp the head to the limit), called at the end of
`DinosaurEntity#tick`.

### The unreported one — namespaced post-shader programs are unloadable on Fabric `<1.21.2`

Vanilla's legacy `PostPass` / `EffectInstance` builds its program id by **concatenating**:

```java
new ResourceLocation("shaders/program/" + name + ".json")
```

The one-argument `ResourceLocation` constructor splits on `:`, so a namespaced program name
(`alexscaves:blur`) yields namespace `shaders/program/alexscaves`, which fails
`Non [a-z0-9_.-] character in namespace of location` and takes the **whole chain** down with it.

Forge and NeoForge patch that constructor. **Fabric does not**, and upstream Alex's Caves was
Forge-only, so this has been broken since the Fabric milestone and was never seen. From 1.21.2
vanilla goes through `ShaderManager.getPostChain` on assets this tree already rewrites in
`migrateShadersTo1212`, where a namespace is legal — so the boundary is **Fabric `<1.21.2` only, 8
nodes**, confirmed empirically rather than assumed: probe boots gave `1.21.1-fabric` **3** failures,
`1.21.4-fabric` **0**, `1.21.11-fabric` **0**, `26.2-fabric` **0**.

Fix: a new `DataPackMigration.unnamespacePostProgramsBelow1212`, wired into `processResources` for
Fabric `<1.21.2` only. It moves `assets/alexscaves/shaders/program/*` to
`assets/minecraft/shaders/program/alexscaves_*`, rewrites the `vertex`/`fragment` references inside
each program JSON and the `passes[].name` references inside each `shaders/post/*.json` to the
flattened `alexscaves_x` spelling, and leaves vanilla ids untouched. `:1.20.1-fabric:processResources`
reports *"Un-namespaced 19 post-shader assets Fabric cannot address"*; the client then boots with
**zero** `Failed to load shader` lines and the hologram renders translucent and glowing instead of
opaque (`screenshots/2026-08-30_17.32.30.png`).

One benign warning survives — *"Shader alexscaves_bumpy could not find uniform named OutSize"* —
which vanilla logs for its own programs too.

**The general trap, worth carrying to any multiloader mod with post-process shaders:** *a loader that
patches a vanilla constructor hides an asset-layout bug from every mod built against it.* Anything
upstream got away with because Forge patched `ResourceLocation` has to be re-checked on Fabric, and
the symptom is a `WARN` in a boot log nobody reads plus an effect that is simply absent.

### #1 and #5 — multipart hitboxes with no client-side entity id (26.2 only)

Both reports are one defect. Seven entities in this mod are multipart owners —
`LuxtructosaurusEntity` (via `SauropodBaseEntity`, the reporter's "boss dino"), `TremorzillaEntity`,
`HullbreakerEntity`, `CorrodentEntity`, `MagnetronEntity`, `QuarrySmasherEntity` and
`GossamerWormEntity` — and each builds its `PartEntity`s in its own constructor.

`Entity.<init>` assigns `this.id = level.getNextEntityId()`. `ServerLevel` overrides that to loop
`ENTITY_COUNTER.incrementAndGet()` until it finds an unused value; the base `Level` returns **0**.
So a part built on the server gets a real id and a part built on the **client** never does. That has
always been true and never mattered, because nothing read a part's id.

**26.2 is the version where it started mattering.** `javap -c` over 14 MC versions:
`Entity.getId()` is a 5-instruction field read on `1.20.1` → `26.1.2`, and a 13-instruction body
carrying `throw new IllegalStateException("Tried to access entity ID before ID assignment")` on
`26.2` alone. Any interact or attack aimed at a part reaches that read, so the first hit on a
Luxtructosaurus, or the first right-click on a Tremorzilla, takes the client down. (Report #5's
`/attribute` scaling is a red herring: it makes the parts easier to hit, not broken.)

Fix: the seven owners override `setId(int)` and, after `super.setId(id)`, hand each part
`parentId + i + 1` through a new `ACMultipartOwner#acAssignPartIds` default. This is **vanilla's own
mechanism**: `EnderDragon` overrides `setId` and assigns `subEntities[i].setId(id + i + 1)` on
1.21.11 and below; on 26.2 vanilla moved the identical arithmetic into `recreateFromPacket`. Our
override still fires there because `LivingEntity.recreateFromPacket` calls `setId` last.

Two things make the hook safe on all 58 nodes rather than only on 26.2:

- It is **client-only in practice.** `setId` is invoked by `recreateFromPacket`, which the server
  never runs; server-side parts already hold real counter values from `ServerLevel`, so
  `ServerLevel.partEntities` and `getEntityOrPart` bookkeeping is untouched everywhere.
- The array is written in the **oldest spelling** (`net.minecraftforge.entity.PartEntity<?>[]`) so
  the NeoForge namespace rewrite and the Fabric `!fab-partentity` redirect both re-point it — see
  the always-on rule about authoring in the oldest spelling.

### #2a — the fog band-aid was gated one boundary too high

`ClientEvents` multiplies the fog distance inside a mod fog volume, and re-reads
`RenderSystem`'s fog start/end as its default so that a foreign mod which set them directly is not
clobbered. That read was gated `//? if >=1.21.6` on the belief that only eventbus 7 changed it.

The real boundary is **1.21.2**, where `setupFog` stopped writing `RenderSystem` and started
*returning* an immutable `FogParameters` that the caller writes later. At event time the getter
therefore holds the **previous frame's** distance — which this method already multiplied. It
compounds every frame: the fog collapses to the camera in a second or two and the world renders as a
flat sheet of the biome's fog colour, flickering as the two passes disagree. Exactly the report:
worst in Toxic Caves, Forlorn Hollows and Abyssal Chasm, which are the strongly-tinted volumes.

The event's own getters are correct from 1.21.2 up on every loader (on Fabric this mod's
`FogSetupMixin` fills them), so moving the gate to `>=1.21.2` is the whole fix.

### #2d — a renderer bound, and an interface a vanilla class was expected to satisfy

Two defects on top of each other, both in the boats:

1. `AlexsCavesBoatRenderer<T extends Boat & AlexsCavesBoat>` — the bound is what the dispatch cast
   is generated against, so it must be the nearest common supertype of **both** AC boats. 1.21.2
   moved chest boats onto their own branch (`ChestBoat` → `AbstractChestBoat` → `AbstractBoat`),
   making them siblings of `Boat`; a `Boat` bound erases to a checkcast the chest boat cannot pass.
   Gated onto `AbstractBoat` from 1.21.2. The registration in `ClientProxy` is raw, which is why it
   compiled. 1.21.11 then moved that class into `…vehicle.boat`, so a new
   `!mc2111-pkg-abstractboat` rule sits beside the existing `!mc2111-pkg-boat`.
2. `AlexsCavesBoat` declared `getRowingTime(int, float)` and relied on the **vanilla superclass**
   supplying the body. That works only where the runtime is Mojmap. On Fabric the vanilla method is
   intermediary-named at runtime, so nothing implemented the interface method and rendering either
   boat threw `AbstractMethodError`. Renamed `acGetRowingTime`, implemented on both entities by
   delegating to the vanilla method.

**The reusable trap: a mod interface may never expect a VANILLA supertype to satisfy it.** Declare
a mod-unique name and delegate. It compiles and runs on Forge/NeoForge and dies on Fabric.

### #3 — Fabric never stamped `minecraft:enchantable`

From 1.21.2 `ItemStack#isEnchantable` is purely `has(DataComponents.ENCHANTABLE)`, and
`EnchantmentMenu` asks it. Forge and NeoForge each have an arm stamping that component from
`ACEnchantableItem#getEnchantmentValue`; **Fabric had none**, so all thirteen enchantable AC items
were unenchantable at a table on 22 nodes.

Enchanted **books** were unaffected — `EnchantmentHelper#getAvailableEnchantmentResults`
special-cases `Items.BOOK` and never looks at the component — which is precisely the asymmetry the
reporter described, and the detail that identified the defect.

Fabric's hook is `DefaultItemComponentEvents.MODIFY`: one callback for the whole registry, fired
after every mod initializer and before the item registry freezes. The builder it hands the modifier
is seeded from `item.components()` by the API itself, so `REPAIRABLE` merging needs no per-version
split of the kind the NeoForge helper needs. `getOrCreate` rather than a plain getter, because
`FabricComponentMapBuilder` has none and `getOrDefault` rejects a null default.

### #4 — the sweetberry "x-ray", not reproduced

`GiantSweetberryBlock` is placed on ice cream, and `IceCreamBlock.getType()` returns `0` exactly
when there is ice cream below — i.e. the reporter's "more than one block of icecream" is the TYPE 0
state. That made the pairing worth taking seriously.

Every occlusion path was walked and every one **under**-occludes, which cannot cull a face that
should draw:

- `IceCreamBlock.getOcclusionShape` is `0..14` for TYPE 0/1 and `2..16` for TYPE 2, against a
  `cube_all` model. The UP face occlusion shape of a TYPE 0/1 block is therefore *empty*, so
  `shouldRenderFace` returns early and draws — extra hidden geometry, never a missing face.
- `isSolidRender` is false for every ice cream state (the occlusion shape is not a full block), so
  the VisGraph never marks those sections opaque and section culling is if anything too weak.
- The berry's own face occlusion shapes are empty on all four sides and 6×6 on DOWN, so it occludes
