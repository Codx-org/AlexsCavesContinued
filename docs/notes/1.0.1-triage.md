## The silent-override trap (the spine of this report)

A mod method written **without `@Override`** keeps compiling after vanilla changes the
supertype's parameter list, silently stops being called from that version up, and **nothing**
reports it — not javac, not `verify_mixins.py`, not a green boot, not a green build. Six of the
twelve reported items were instances of it.

`scripts/override_audit.py` is the detector, with **two limits that both bit during this cycle**:

1. **It reads COMPILED classes.** Its output is stale for any node not freshly recompiled — a
   fix can be verifiably in source and still be reported on 19 nodes. Recompile, then audit.
2. **It under-reports.** `MetalBarrelBlock.use` and `RemoteDetonatorItem`'s methods were absent
   from its 1673 findings. Treat the output as a lower bound and read reported classes directly.

Known false-positive families still to suppress inside it. The 58/58 run is now at **916
findings, every one of them in a family below** — zero unexplained rows. (It was 917 while
`DesolateDaggerItem.getMaxDamage` was still outstanding; that row is the one that has since been
fixed and is gone, which is what the drop of exactly one is.)

| family | count | why it is not a defect |
|---|---|---|
| `lerpMotion(DDD)` | 336 | a real bridge IS emitted by `stonecutter.gradle.kts` ~3095 |
| `*Model.animate(IAnimatedEntity)` | 242 | Citadel's own method; pure name collision with `Model.animate(AnimationState, …)` |
| `getToolModifiedState` | 84 | **loader-package mismatch** — see below |
| `trigger(ServerPlayer)` | 58 | `ACAdvancementTrigger`'s mod-internal convenience overload |
| `scale(...)` | 58 | erasure bridge (`BrainiacRenderer` et al.) |
| `getEquipmentSlot()` | 42 | `GalenaGauntletItem`; dead upstream too |
| `getAttributeModifiers` | 28 | the seven already-gated items |
| `canBeRiddenUnderFluidType` | 26 | **loader-package mismatch** |
| `canPerformAction` | 13 | **loader-package mismatch** |
| `getExpDrop` | 11 | `RadrockUraniumOreBlock`, already two-armed |
| `getQuads` | 10 | **loader-package mismatch** (`fabric/forge/**` `BakedModelWrapper`) |
| `getDefaultAttributeModifiers` | 7 | the same seven items |
| `getSoundType` | 1 | `PewenBranchBlock`; both arms verified live (see below) |
| ~~`getMaxDamage`~~ | 0 | `DesolateDaggerItem` — **this one was real** and is now FIXED; the row no longer appears |

**The loader-package mismatch is the audit's third limit.** It resolves the mod's declared
descriptor against whichever supertype it can find, which for these hooks is the **Forge**
(`net.minecraftforge.*`) one — while the class it is reading was compiled for NeoForge
(`net.neoforged.neoforge.common.ItemAbility`, `…neoforge.fluids.FluidType`) or for Fabric (the
mod's own `fabric/forge/**` stand-ins). Same method, different package, so the descriptors never
match and never will. Not a defect; do not chase these again.

### ⚠️ `scripts/mcjavap.py` had a blind spot, and it caused two wrong band boundaries

`jar_for(mc)` only matched loom's **`<loader>-<mc>-<build>-minecraft-merged/`** directory. A
plain **Fabric** node's jar lives under the *shared* `minecraft-merged/` directory with the MC
version in the **child** folder name (`minecraft-merged/1.21.2-loom.mappings…/…jar`), so the
four MC versions this matrix reaches on Fabric only — `1.20.3`, `1.20.5`, `1.21.2` (and
`1.21.2-neoforge`, which has no Forge sibling either) — resolved to nothing. Every caller that
treats a miss as "skip" silently stopped covering them, so their bands were inferred from
neighbours and both landed **one MC version too high**:

| what | recorded | truth (javap'd out of the real jar) |
|---|---|---|
| `Block.getCloneItemStack` takes `LevelReader` | ≥1.20.4 | **≥1.20.3** (1.20.1/1.20.2 take `BlockGetter`) |
| `LivingEntity.getBaseExperienceReward` takes `ServerLevel` | ≥1.21.3 | **≥1.21.2** (1.21.1 is `protected int getBaseExperienceReward()`) |

Both were hard compile failures on exactly those nodes, which is the only reason they were
caught. `jar_for` now falls back to the shared layout.

⚠️ **`scripts/override_audit.py` carried its OWN copy of the same buggy lookup** (a second
`vanilla_jar()` at ~line 159), so fixing `mcjavap.py` alone changed nothing — the audit still
printed *"skipped … 1.20.3-fabric 1.20.5-fabric 1.21.2-fabric 1.21.2-neoforge"*. It now
`import mcjavap` and delegates, translating `jar_for`'s `SystemExit` back to `None`, so there is
**one** place that knows loom's two cache layouts. First run with real 58/58 coverage:
**917 findings, no skip line** (was 860 over 54 nodes). The four newly-visible nodes contributed
57 rows, of which all but two are the known families; the two singletons were each worth a look
and split one-and-one:

- `PewenBranchBlock.getSoundType(BlockState, LevelReader, BlockPos, Entity)` on `1.21.2-neoforge`
  — **not a defect.** Probed every NeoForge build in the matrix (20.4 → 26.2) plus Forge 1.20.1:
  `IBlockExtension`/`IForgeBlock` declares that exact four-argument overload on **all 36**
  Forge/NeoForge nodes, and the `//? if fabric` arm supplies vanilla's one-argument form.
- `DesolateDaggerItem.getMaxDamage(ItemStack)` on `1.20.3-fabric` — **real**, and worse than the
  single node suggests. See the worklist.

**The rest of the tree was then swept for the same error** (any band stated as starting at
1.20.4, 1.20.6 or 1.21.3 — i.e. one above a Fabric-only version — shares the blind spot). There
are exactly **two** such `//?` gates in `src/main/java` (`NuclearFurnaceResultSlot:52`,

## Report #6 — smithing table crash: SOLVED

ℹ️ **The report's trailing *"Anvil and enchantment table is not"* is consistent with the cause and
needs no separate investigation.** The crash is an *entity preview* built by hand — only
`SmithingScreen` does that. The anvil and the enchantment table render no entity, so they were
never going to crash, which is exactly what the reporter observed.

**Reproduced locally on `26.2-fabric`** (dev client, `/setblock ~ ~1 ~2 minecraft:smithing_table`
then right-click) — the report needs no log from the reporter any more.

```
Description: Rendering entity in world
java.lang.NullPointerException: Cannot invoke "…LivingEntity.getUUID()" because "rendered" is null
    at …client.event.ClientEvents.acPreRenderLiving(ClientEvents.java:159)
    at …client.event.ClientEvents.preRenderLiving(ClientEvents.java:198)
    at …fabric.event.ACEventBus.post(ACEventBus.java:105)
    at LivingEntityRenderer.handler$…$ac_fabricPreRenderLiving(LivingEntityRenderer.java:2564)
    at ArmorStandRenderer.submit(ArmorStandRenderer.java:73)
    at EntityRenderDispatcher.submit(EntityRenderDispatcher.java:154)
    at GuiEntityRenderer.renderToTexture(GuiEntityRenderer.java:39)
    at PictureInPictureRenderer.prepare / GuiRenderer.preparePictureInPictureState / GuiRenderer.render
```

**Cause — a render state that never came from an entity.** From 1.21.2 the loaders' render events
hand out an `EntityRenderState` instead of the entity, so this tree recovers the entity from the
duck that `mixin.renderstate.EntityRendererMixin` stamps at `EntityRenderer#extractRenderState`
HEAD (`ACStateAccess`). That covers every state vanilla *extracts*. It does not cover a state
vanilla **constructs by hand** — and 1.21.9 moved the GUI's entity previews onto picture-in-picture
rendering, where (javap'd on 26.2) `SmithingScreen`'s constructor does exactly that:

- `SmithingScreen.<init>`: `new ArmorStandRenderState()`, then `entityType` / `showBasePlate` /
  `showArms` / `xRot` / `bodyRot` assigned field-by-field; `updateArmorStandPreview(ItemStack)`
  fills the equipment slots. **`extractRenderState` never runs, and there is no armour-stand entity
  anywhere** — the preview is pure data.
- `SmithingScreen.extractRenderState` passes that state to `GuiGraphicsExtractor.entity(...)`;
  `GuiEntityRenderer.renderToTexture` then calls `EntityRenderDispatcher.submit(state, …)` →
  `ArmorStandRenderer.submit` → the mod's `RenderLivingEvent.Pre` dispatcher, with a null entity.

That is why the **anvil and the enchanting table are fine** — they render no entity — while the
smithing table dies on open. Same reason the player inventory is fine: `InventoryScreen` builds its
preview through `EntityRenderer#createRenderState(entity, partialTick)`, which *does* call
`extractRenderState`, so the duck is stamped there.

**Fix.** `ClientEvents.acPreRenderLiving` returns `false` and `acPostRenderLiving` returns early
when the entity is null — there is nothing either hook can do for a preview. Both were the only
**unguarded** `ACStateAccess.entity(...)` dereferences in the tree; audited all 11 consumers:

| consumer | status |
|---|---|
| `ClientEvents.acPreRenderLiving` / `acPostRenderLiving` | **were unguarded — fixed** |
| `StateRenderLayer.draw` | already `if (entity == null) return;` |
| `ACArmorRenderProperties`, `HumanoidArmorLayerMixin` ×3, `citadel/LivingEntityRendererMixin`, `citadel/HumanoidModelMixin` ×4 | `instanceof`-guarded ⇒ null-safe |
| `ArrowRenderer.getTextureLocation` | unguarded, but no GUI path constructs an arrow state |
| `LivingEntityRendererEventsMixin` ×6 | reads `partialTick`, not the entity |

**Band: 1.21.9 → 26.2, all three loaders** (the versions with GUI picture-in-picture entity
rendering). Compile-verified on `26.2-{fabric,forge,neoforge}`, `1.21.8-fabric` and `1.20.1-forge`.

**Runtime-verified on the patched build** (2026-08-23, `26.2-fabric`, same reproduction —
`/setblock ~3 ~1 ~ minecraft:smithing_table`, `/tp @s ~ ~ ~ -90 3`, then use): the screen opens to
"Upgrade Gear" and **the armour-stand preview draws** — i.e. the entity-less render state still
reaches `ArmorStandRenderer.submit`, the guard simply declines to do anything with it, which is the
intended behaviour rather than the preview being suppressed. Client process alive afterwards, no new
file in `versions/26.2-fabric/run/crash-reports/`.

## Report #5 — the raycat glow: NOT a regression

**Verdict: the raycat renders the same on every render era this tree spans.** Matched-rig A/B on
`1.20.1-forge` (= upstream, the reference), `1.21.5-fabric` (first *RenderPipeline* node) and
`26.2-fabric` (deferred-submit + reversed-Z): identical halo extent, identical textured body with a
bright emissive face, no hard-edged rectangle around the glow, and the same brightness. Whatever the
reporter photographed, it is not a cross-version drift in the irradiated effect — **their MC version
and a viewable screenshot are now the blocker**.

⚠️ **The single-frame brightness metric that started this was measuring the shader, not the port.**

## Report #2 — the primordial "pinwheel": it is the Ambersol shine, drawn correctly

Reproduced in-world on `26.2-fabric` at `[810, 28, 1167]` (`/locate biome alexscaves:primordial_caves`):
white starburst wedges radiating from a single vertex, embedded in the cave walls. At 500 % it reads as
geometry collapsing to a point — the classic look of a degenerate or NaN vertex — which is why it was
filed as undiagnosed. It is neither.

**It is `AmbersolBlockRenderer`.** The renderer fans `lights` (a `pos.asLong()`-seeded `4..8`) triangles
around the block centre, billboarded to the camera, each drawn as a degenerate quad
`origin, left, right, left` into `ACRenderTypes.getAmbersolShine()`. The origin vertex is
`(255,254,233, α230)` and both outer corners are `(215,89,32, α0)`, blended
`SRC_ALPHA, ONE, ONE, ONE_MINUS_SRC_ALPHA` — additive. Barycentric interpolation gives constant alpha
*across* a wedge and falloff only *along* it, so **the hard straight edges are inherent to the shape**,
not a symptom.

### What was checked, and how

Sealed A/B with `scripts/block_shots.sh` — one block against open sky, pinned time, spectator, exact
position *and* rotation, five-block volume cleared, four consecutive frames:

| check | `1.20.1-forge` (upstream parity) | `26.2-fabric` | verdict |
|---|---|---|---|
| wedge count / fan geometry | 9 wedges | 9 wedges | identical |
| added light, recovered by diffing an `air` background frame | warm, `R>G>B` | warm, `R>G>B` (`(106,81,13)` near the block, decaying to nothing) | identical |
| occluded by solid stone (`scripts/block_occlusion_test.sh`) | plain stone, no bleed | plain stone, no bleed | identical |

The 26.2 frame *looks* whiter only because that rig player carries permanent night vision: an additive
draw over a brightened background saturates. Diffing the background out removes the difference entirely.

### Why it reads as a bug to a player

The fan is billboarded at the **block's** depth plane and spreads several blocks sideways, so wedges
emerge into open air with their source block hidden behind rock — a starburst with no visible cause.
That is upstream art direction, and it has a client toggle already
(`AlexsCaves.CLIENT_CONFIG.ambersolShines`, checked at the `AFTER_TRANSLUCENT_BLOCKS` dispatch in
`ClientEvents`). ⚠️ **Do not "fix" it** — any change here diverges from upstream for every node.

What the reporter almost certainly saw on shipped `1.0.0` is the row above it: **the reversed-Z depth
bug**, which made every render type in the mod x-ray through terrain on 26.2 and is already fixed

## Report #9/#9b — the compendium and the spelunkery table: four silent bugs, stacked

Reproduced on `26.2-fabric`: `/give @s alexscaves:cave_book`, press use — the world darkens,
the HUD dims, **nothing is drawn**, and the screen eats input until Escape. That a screen really
was open (rather than it merely being night) was proved by sending `/say SCREEN-OPEN-TEST`, which
never appeared because the chat key was swallowed; after Escape, `/say AFTER-ESCAPE` appeared
and the world was bright daylight.

Nothing is logged for either bug. The whole search had to be done by instrumentation.

**Bug 1 — the book model never left its recorder.** From 1.21.6 a screen cannot draw a 3D model
inline; it submits a `PictureInPictureRenderState` and a `PictureInPictureRenderer` rasterises it
into its own texture. Three temporary `ACBOOKDBG` probes (state constructor, mixin lookup,
`renderToTexture`) all fired every frame — `state submitted 427x240`, `lookup hit, original=null`,
`renderToTexture running` — so the whole picture-in-picture chain worked and the failure was
downstream of it. It was in `CaveBookPipRenderer.renderToTexture`'s `>=26.2` arm, which built an
`ACSubmitBuffers` around the frame's `SubmitNodeCollector` and **never called `flush()`**. An
`ACSubmitBuffers` *records*; nothing reaches the frame until the recording is handed to the
collector. 26.2-only, because the band below is handed a real immediate-mode `BufferSource` that
the game ends itself. Every one of the other 18 construction sites in the tree flushes;
`scripts/submit_flush_audit.py` now keeps that invariant (19 sites, 0 misses).

**Bug 2 — the pages were drawn into the wrong buffer source.** With bug 1 fixed the book drew,
with **blank pages**. `PageRenderer.renderPage` ignored the buffer source the book model was
being drawn into and fetched its own, `Minecraft.getInstance().renderBuffers().bufferSource()`.
Below 26.2 those are the same object, so it never mattered. On 26.2 there is no
`Minecraft#renderBuffers()` and that call resolves to `ACRenderContext.bufferSource()` — the
**level** pass's shared source, whose collector is pushed only inside `LevelRenderer#submitFeatures`
and is therefore `null` while the book is being rasterised. `ACClientCompat.drawInBatch`'s 26.2 arm
returns early on a null collector, so every glyph, page number, item and widget was dropped without
a word. Fixed by threading the real buffer source down
`renderBookModel` → `renderBookContents` → `renderForPageType` → `PageRenderer#renderPage` →
`BookWidget#render`, widening those signatures from `MultiBufferSource.BufferSource` to
`MultiBufferSource`. A no-op on every band below 26.2, where the threaded object is the one that
was being fetched anyway.

⚠️ **The general shape, worth carrying to any other GUI that draws a model.** On 26.2 "draw" means
"record, then hand the recording to *this* pass's collector". A draw call that reaches the wrong
collector, or none, is not an error — it is a no-op. So the two questions to ask of any legacy
render body on that version are *who flushes this?* and *whose collector am I on?*, and neither
has an answer in the log.

**Bug 3 — vanilla deleted `Font#adjustColor` at 1.21.6, so every `0xRRGGBB` text colour became
alpha 0.** With bugs 1 and 2 fixed the book drew, page furniture and all, and the pages were
**still blank**. A temporary `ACBOOKDBG_HIDE_MODEL` flag in `CaveBookScreen` removed the book
model entirely and the text still did not appear, which ruled out occlusion and proved the glyphs
were never rendered rather than being drawn behind something.

The cause is in vanilla, not in the mod. Up to and including **1.21.5**, both `Font#drawInternal`
overloads *and* `drawInBatch8xOutline` (on the colour **and** the outline colour, never on
`backgroundColor`) opened with

```java
private static int adjustColor(int c) { return (c & 0xFC000000) == 0 ? ARGB.opaque(c) : c; }
```

From **1.21.6** that method does not exist and the colour goes straight to the glyph quads, so a
literal with no alpha byte means alpha 0: the text is submitted, batched and drawn completely
transparent. **Nothing is logged and nothing throws.** Verified by `javap` on the loader-patched
jar of all 22 MC versions in the matrix — fixup present `1.20.1`…`1.21.5`, absent
`1.21.6`…`26.2`. `GuiGraphics` has no fixup of its own on 26.2 either.

That is a **22-node** bug, not a 26.2 one, and it is why the *spelunkery table* (report #9) looked
dead too: its title, its "attempts" line, its highlight and its word buttons are all
`0X99876C`/`0X000000`/`4210752` literals. On 26.2 the two failures were indistinguishable, because
bug 2 was already dropping the same glyphs.

The fix is one helper, `ACColors.opaque`, doing exactly what vanilla used to:

```java
public static int opaque(int argb) { return (argb & 0xFC000000) == 0 ? argb | 0xFF000000 : argb; }
```

Below 1.21.6 it is a no-op the game would have performed anyway, **so call sites need no `//?`
gate** — one ungated wrap is right on all 58 nodes. Applied inside `ACClientCompat`'s three text
wrappers (so every site that already goes through them is fixed at once) and at the handful of raw
`GuiGraphics.drawString` sites that do not: `SpelunkeryTableScreen` (×6), `SpelunkeryTableWordButton`,
`NuclearFurnaceScreen` (×2), plus `CaveMapRenderer`'s two `0X87695B`/`0XEBDCC2` constants.
`scripts/text_alpha_audit.py` is the standing detector — it parses the colour argument of every
text-draw call site, skips the ones that route through the wrapper, and fails on any literal whose
alpha byte is empty. Currently 0.

**Bug 4 — the 26.2 `String` text path lost `§` formatting.** With bug 3 fixed the pages finally
drew, with every legacy formatting code printed as two literal glyphs. `ACClientCompat`'s `>=26.2`
`drawInBatch(Font, String, …)` arm was building its sequence with
`FormattedCharSequence.forward(text, Style.EMPTY)`, which is `StringDecomposer.iterate` — a
**verbatim** walk. Vanilla's own `String` path is `bidirectionalShaping` followed by
`StringDecomposer.iterateFormatted`, i.e. `§` codes are *style*, not characters. Swapped to that.
Only the 26.2 arm was ever wrong; the band below hands the string to `Font#drawInBatch` itself.

⚠️ **The reusable lesson is bug 3, and it is not specific to this mod.** Any mod carrying
`0xRRGGBB` text colours from before 1.21.6 draws invisible text from 1.21.6 up, silently. The tell
is text that is *missing* rather than *wrong*, on a version boundary that has nothing to do with
the GUI code that stopped working. `ClientSackOfSatingTooltip` already carried a local comment
noting the trap on one line without generalising it — one call site had been noticed and fixed
years before the other forty.

### Root cause: `@Redirect` and `@ModifyConstant` are EXCLUSIVE injectors

Only one mod may redirect a given instruction. Mixin keeps whichever applicator ran **first**,
logs `"@Redirect conflict. Skipping …"` for the loser, and the loser's `"defaultRequire": 1`
then throws `InjectionError: Critical injection failure: … (0/1) succeeded`. That fails the whole
class transformation, so **both** mods die — the crash is not "AMC's fault" or "Citadel's fault",
it is whichever of the two lost the race.

⚠️ **`@ModifyConstant` collides the same way** — it is implemented as a `RedirectInjector`
subclass. This is why the Citadel repro crashed at a *server* mixin (`ServerLevel#tickTime`'s
`1L`) long before any render mixin ran, and why the fix had to widen from 2 files to 6.

Because Citadel is **vendored** here (93 relocated classes + 13 mixins, see `docs/notes/citadel.md`),
this mod duplicates Citadel's entire mixin set against vanilla. So it is not one unlucky
instruction: *every* exclusive injector in the overlap collides with real Citadel, and AMC — which
depends on real Citadel and carries its own copy of the outline hook — collides on the render one.

### The fix: MixinExtras composing injectors

`@WrapOperation` and `@ModifyExpressionValue` are **late** injectors, applied after every vanilla
redirect. They wrap whatever the instruction has already become, so the other mod's redirect runs
as `original.call(...)` and both hooks survive. Both accept `method` / `at` / `slice` / `remap` /
`require` / `expect` / `allow` / `order` (confirmed by javap on `mixinextras-fabric-0.5.3.jar`), so
the conversion is annotation-name + one extra handler parameter, with the Stonecutter-gated
`method` arms and `expect` counts untouched. `@ModifyExpressionValue` reaches a constant via
`@At(value = "CONSTANT", args = "longValue=1")` — the `args` spelling, not `constant = @Constant`.

MixinExtras is available on every node: Fabric Loader and NeoForge bundle it, and
`build.forgeg.gradle.kts` already ships `mixinextras-forge` on Forge builds below 60.1.11.

Six vendored-Citadel mixins converted:

| file | was | now |
|---|---|---|
| `mixin/client/citadel/OutlineColorMixin.java` | `@Redirect` `Entity;getTeamColor()I` | `@WrapOperation` |
| `mixin/client/citadel/SkyTimeOfDayMixin.java` | `@Redirect` `ClientLevel;getTimeOfDay(F)F` | `@WrapOperation` |
| `mixin/citadel/ServerLevelMixin.java` | `@ModifyConstant` `longValue = 1L` | `@ModifyExpressionValue` `args = "longValue=1"` |
| `mixin/client/citadel/ClientLevelMixin.java` | `@ModifyConstant` `longValue = 1L` | same |
| `mixin/citadel/MinecraftServerMixin.java` | `@ModifyConstant` `longValue = 50L`, `expect = 4` | `@ModifyExpressionValue` `args = "longValue=50"`, `expect = 4` |
| `mixin/client/citadel/SplashRendererMixin.java` | `@ModifyConstant` `intValue = -256` / `16776960` | `@ModifyExpressionValue` `args = "intValue=-256"` / `"intValue=16776960"` |

`SkyTimeOfDayMixin`'s handler deliberately does **not** call `original` — it replaces the time of
day outright, which is what the `@Redirect` did.

`mixin/client/citadel/LevelRendererMixin.java` was deliberately **left** as a `@Redirect`
(`OutlineBufferSource;endOutlineBatch()V`). Citadel's counterpart there is an `@Inject`, so there
is no conflict, and the ≥1.21.2 arms select through a regex (`/lambda\$addMainPass\$/`) plus
loader-specific `method_62214` spellings that a conversion would put at risk for no reported gain.

is not one. Proof it is the rig: javap on the loom-patched named jar finds **0** occurrences of
`f_135042_`, while `citadel.refmap.json` maps `addAdditionalSaveData`→`m_7380_` etc. The valid
route is loom's own remapper, via a throwaway `"modLocalRuntime"(files(<jar>))` dependency driven
by a `-P` property. `build.forgeg.gradle.kts` already documents the identical trap for codxlib.
The probe used here was **reverted** after the run; do not look for it in the tree.

### W4 — the acid crash, and why no `//?` gate could have fixed it

Player's report, NeoForge **26.1.2.97**, `alexscaves@1.0.0`:

```
java.lang.IllegalArgumentException: Cannot look up tracker by tag for non-vanilla fluid:
    TagKey[minecraft:fluid / alexscaves:acid]
  at EntityFluidInteraction.getFluidTypeByTag(EntityFluidInteraction.java:255)
  at Entity.isEyeInFluid(Entity.java:1636)
  at ACFluids.isEyeInAcid(ACFluids.java:103)
  at ClientEvents.fogColor(ClientEvents.java:1153)
```

**NeoForge reintroduced `FluidType` into `EntityFluidInteraction` between builds `26.1.2.87` and
`26.1.2.97` — same MC version, both live in the wild.** On `.97` the `trackerByFluid` map is keyed
by `FluidType`, the constructor's `Set<TagKey<Fluid>>` loop is commented out, and every
`TagKey`-shaped method routes through `getFluidTypeByTag`, which hard-throws for anything that is
not water or lava. The mod's `EntityMixin#ac_trackModFluids` `@ModifyArg` widening of the tracked
tag set therefore stopped taking effect, and `Entity#isEyeInFluid(TagKey)` became a guaranteed
throw for `alexscaves:acid`.

⚠️ **This tracks the loader BUILD, not the MC version.** Stonecutter gates and
`replacements.string` rules are both keyed on the MC version, so *neither can express it* — one
jar has to be correct on `.87` and `.97` at once.

The fix is to stop asking the loader. `ACFluids` is now **ungated** (all seven `//? if >=26 ||
fabric` arms deleted) and self-computes from `Level#getFluidState` — pure vanilla API, byte-identical
across all 58 nodes:

- `fluidHeight(entity, tag)` walks the entity's deflated bounding box, skipping unloaded chunks, and
  returns the deepest matching fluid surface above `box.minY`. A `null` tag means *any* fluid.
- `isEyeInFluid(entity, tag)` samples the single block at eye level (minus vanilla's `0.11111111`
  drop) and compares the fluid's surface height against the eye.

Three side benefits: one implementation instead of two, the **active node now exercises it** (it
used to compile only the loader-delegating arm), and `isInAnyFluid`/`maxFluidHeight` regained
third-party-fluid awareness that the `>=26` rewrite had narrowed to a fixed list.

`EntityMixin` is deliberately **unchanged**. Its `>=26` `@ModifyArg` is now redundant for queries but
harmless (the `<init>(Ljava/util/Set;)V` target is unchanged even on `.97`), and its `fabric && <26`
`@Inject` at TAIL of `updateInWaterStateAndDoFluidPushing` is what actually supplies **push
physics** on Fabric's 18 sub-26 nodes — that one must stay.

### The bytecode proof that the crash path is gone (26.1.2-neoforge, compiled against .97)

`javap -p -c` over **every** compiled mod class on that node, grepping for the whole family
(`isEyeInFluid`, `getFluidHeight`, `EntityFluidInteraction`, `getFluidTypeByTag`,
`getFluidTypeHeight`, `isInFluidType`, `getMaxHeightFluidType`, `getEyeInFluidType`):

- `ACFluids` itself calls **only** `Level.getFluidState`, `Level.hasChunkAt`,
  `FluidState.{getHeight,isEmpty,is}`, `AABB.deflate`, `BlockPos.{containing,getY}`,
  `BlockPos$MutableBlockPos.set` and `Entity.{level,getBoundingBox,getEyeY,getX,getZ}`. Nothing
  from the loader, nothing that can throw.
- Exactly **two** vanilla `isEyeInFluid(TagKey)` call sites survive anywhere in the mod —
  `CommonEvents:370` (diving helmet) and `MagneticWeaponEntity:340` — and **both pass
  `FluidTags.WATER`**, which is one of the two tags `.97`'s `getFluidTypeByTag` still answers.
- Every other hit in the tree is a comment or javadoc.

- `EntityMixin`'s `>=26` `ac_trackModFluids` `@ModifyArg` is **inert on `.97`, not dangerous**.
  `javap`'d straight out of `minecraft-patched-26.1.2.97.jar`: the
  `EntityFluidInteraction(Set<TagKey<Fluid>>)` constructor still takes the set and still iterates it,
  but the loop body is empty (`checkcast TagKey; astore_3; goto` — the element is loaded and
  dropped), so widening the set adds nothing and, crucially, never reaches `getFluidTypeByTag`. The
  mixin's `@At` target descriptor is unchanged, which is why `verify_mixins.py` is green on that node.
- The accepted-tag set of `.97`'s `getFluidTypeByTag` is exactly **`FluidTags.WATER` and
  `FluidTags.LAVA`**, compared by reference (`if_acmpne`), everything else falling straight to
  `new IllegalArgumentException`. Four `TagKey`-shaped methods route through it —
  `applyCurrentTo`, `getFluidHeight(TagKey)`, `isInFluid(TagKey)`, `isEyeInFluid(TagKey)` — so any
  one of the four with a mod tag is the same crash.

So on `.97` there is no reachable path to `Cannot look up tracker by tag for non-vanilla fluid`.
This is worth re-running after any change to `ACFluids` or `EntityMixin`: the standing rule here is
that a green build proves the shapes exist, not that nothing calls the broken one.

### One deliberate divergence from vanilla in the rewrite

Vanilla's `Entity#updateFluidOnEyes` carries a **boat exemption**: if the vehicle is a `Boat`, is
not itself underwater, and its bounding box straddles the eye Y, the fluid-at-eyes check is skipped
entirely. `ACFluids#isEyeInFluid` does **not** reproduce it, on purpose.

Reproducing it properly needs an `instanceof Boat` — and the class is `Boat` below 1.21.2 and
`AbstractBoat` from there, so it would be another gate. The tempting version-neutral approximation
("skip when *any* vehicle's bbox contains the eye") is **worse than omitting it**: this mod has
large rideable mobs whose bounding boxes swallow the rider's eye, so that rule would suppress acid
fog for anyone riding one, which is a real bug. Vanilla's exemption, by contrast, almost never
fires — a floating boat keeps the eye above the surface, and a submerged one fails
`isUnderWater()`. The whole cost of leaving it out is at most a frame of fog while a boat bobs in
acid. Do not "fix" this without the gated `Boat`/`AbstractBoat` check.

### Falsified along the way (do not re-walk)

- `FluidState.is(TagKey)` looked deleted at 26 — it is not. At 26 the `is` overloads moved onto
  `net.minecraft.core.TypedInstance<Fluid>`, which `FluidState` implements, so the call resolves
  ungated on all 58 nodes.

### ⚠️ Fabric API was missing as a dependency on EVERY fabric version — 1.0.0 included

Caught by the user after the 1.0.1 upload. `scripts/modrinth_upload.py` hardcoded a
single-element dependency list holding only `CODXLIB_PROJECT_ID`, while every fabric jar's
generated `fabric.mod.json` declares a hard per-MC-version floor (`fabric-api >=0.92.11+1.20.1`
on 1.20.1 … `>=0.155.2+26.2` on 26.2). Modrinth metadata and the jar manifest therefore
disagreed: launchers had no reason to install Fabric API, so the mod installed and then failed
to start.

- Fixed in the uploader by a `version_dependencies(loader)` helper — Fabric API (`P7dR8mSH`)
  is appended on **fabric nodes only**, project-level, so Forge/NeoForge keep codxlib alone.
- `scripts/fix_fabric_api_dep.py` retro-patches published versions and is idempotent (it
  re-reads each with `GET /v2/version/{id}`, never the cached listing). Ran it over the live
  project: **44/44 fabric versions fixed — 22 on 1.0.1 and 22 on the already-shipped 1.0.0.**
- ⚠️ **The PATCH read-back lags.** The first pass reported 12 "not readable back"; all 12 were
  fine on a re-run, and a third pass read `already-ok=44 fixed=0 failed=0`. **Re-run the
  idempotent fixer rather than investigating a failure.**
- ⚠️ **CurseForge cannot be fixed this way.** CF relations have no API field and carry no
  version, so `codxlib` *and* `fabric-api` both have to be added by hand in the web UI.
